RPCEmu Extended Edition 1.1.17. Twelve commits since 1.1.16.

A maintenance release for the 1.1.x series, and a substantial one: a fault that
left every newly created machine with a half-built `!Boot`, two crashes on
macOS, and RISC OS 3.7x and 4.x running at a fraction of the speed they should.

## Every download now contains both emulators

`rpcemu-recompiler` translates ARM code into your processor's own and is the one
to use. `rpcemu-interpreter` executes instructions one at a time: far slower, and
exactly what you want when something behaves oddly and you need to rule the
recompiler out. Reporting a fault that happens on one and not the other says a
great deal in a single sentence.

Until now each download carried whichever one that platform had settled on, and
building the other meant building the whole emulator yourself. Every archive now
has both, on every platform and every architecture. On Windows and Linux they sit
side by side; on macOS the application runs the recompiler and the interpreter is
inside the bundle, at `RPCEmu.app/Contents/MacOS/rpcemu-interpreter`.

This also retires a wrinkle worth knowing about if you have chosen between the
two Windows downloads before: the arm64 one used to be the interpreter while
everything else shipped the recompiler, a difference of several times the speed
with nothing in the file name to say so. Both Windows archives now carry both
binaries and differ only by architecture.

## A new machine came up with most of its !Boot missing

Creating a machine and booting it left `!Boot.Choices.Boot` mostly empty, and the
files had to be copied out of `!Boot.RO5nnHook.Boot` by hand. It happened on
macOS, Linux and Windows alike, and only when the option to set up networking was
used.

RISC OS builds `Choices` on the first boot by copying the hook for the ROM it is
running, and it decides whether to do that with a single test: if
`!Boot.Choices.Boot` already exists, the copy is skipped and nothing else ever
populates it. The disc image ships `Choices` empty for exactly that reason. Our
network template delivered its startup file inside `Choices.Boot`, which created
that directory before the machine had ever been booted, so the first boot
silently did nothing.

Behind it was a second fault. The disc's own hook ships a `SetupNet` that starts
ShareFS, and RISC OS filenames are case-insensitive, so our `SetUpNet` was the
same name - meaning the option that promises Access sharing was suppressing the
file that provides it. The network file now goes into the hooks under a name of
its own and arrives in `Choices` with everything else.

**A machine created with an earlier build stays broken**, since the first boot
has already happened. The repair is the one found by hand: copy the contents of
`!Boot.RO5nnHook.Boot` into `!Boot.Choices.Boot`.

Reported by **Chris Gransden**, and diagnosed by **David Pitt**, who worked out
that it turned on the networking option before anyone had looked at the code.

## Two crashes on macOS

**Stopping a machine while a dialogue was open** aborted the emulator. Every
dialogue belongs to the machine window and lives on the stack, so closing the
window from inside one destroyed it underneath, and the process died at the very
end of an otherwise clean shutdown - everything already safely written, which is
why it looked like a crash from nowhere.

**Choosing Shutdown from the RISC OS Task Manager** did the same thing, by the
same route: RISC OS asks the machine to power itself off, and the emulator turned
that into an immediate forced close. Reported by **pittdj**
([#194](https://github.com/andrewtimmins/rpcemu-extended/issues/194)). His report
did not include the part of the crash log that names the failing function, so
this one is a fix for a real fault on exactly that path rather than a confirmed
reproduction of his; if a shutdown still misbehaves, please reopen with the full
report.

Both paths now wait for anything on screen to close before taking the window
down.

## Scrolling with a trackpad

Scrolling jumped up and down instead of scrolling, while a mouse on the same
machine behaved. The emulator gave RISC OS one scroll click for any wheel event,
in the direction it reported - right for a mouse, where one detent is one event,
and wrong for a trackpad, which sends a stream of small movements whose direction
flickers at the start and end of a gesture. Rotation is now added up and a click
sent per full notch, and sideways gestures are ignored rather than scrolling the
window vertically.

Reported by **pittdj**,
[#197](https://github.com/andrewtimmins/rpcemu-extended/issues/197).

## RISC OS 3.7x and 4.x are fast again

They ran at a fraction of RISC OS 5's speed on the same machine. A 26-bit RISC OS
on a StrongARM changes the CPU's word size twice for every SWI - about sixty-three
thousand times a second - and the recompiler was emptying its entire cache of
translated code each time. It was compiling millions of blocks a second and
throwing every one away, which is a JIT used as a very expensive interpreter.

Translated blocks now record the word size they were built for and are kept, so
the cache survives. Reported by **hubersn**,
[#181](https://github.com/andrewtimmins/rpcemu-extended/issues/181).

## The rest

- **The first shifted keystroke of a session came out unshifted** on macOS, and
  Ctrl or Alt combinations could arrive without their modifier. The emulator let
  go of held keys whenever it believed a menu had opened, and on macOS the event
  it watched for fires constantly with no menu ever pulled down. Reported by
  **DrDavidGee**,
  [#183](https://github.com/andrewtimmins/rpcemu-extended/issues/183).
- **Quitting crashed on macOS, every time, since 1.1.16** - a dialogue raised on
  a window that was already being destroyed. Reported by **DrDavidGee**,
  [#184](https://github.com/andrewtimmins/rpcemu-extended/issues/184).
- **A new machine can set up RISC OS networking for you**, so the guest comes up
  with an address and Access sharing without configuring it by hand.
  **David Ramsden**.
- **The Windows arm64 build is published as a release asset.** It was built and
  tested every time and then offered only as a workflow artifact that expired
  after ninety days.
- **The macOS bundle no longer carries wxWidgets twice.** 1.1.16 shipped two
  copies of the same library under different names.

## What is not proven here

The macOS faults above were found and fixed on an Apple Silicon Mac. The Windows
and Linux builds are verified by CI - which boots RISC OS on each of them and
checks it draws - and by nobody's hands. The trackpad fix in particular wants a
trackpad in front of it.

RPCEmu Extended Edition 1.1.19. Fifteen commits since 1.1.18.

Mostly a debugger release. The Machine Inspector arrived in 1.1.17 and the first
people to use it in anger have been reporting what it is like to work with; this
is that list, largely answered, plus two expansion-card fixes and the full-screen
fault from 1.1.18 finally understood.

## The Machine Inspector is a usable debugger now

Twenty-odd observations from somebody stepping through his own module's code
against his own assembler source. Most of them are here.

**Reading the disassembly.** Four options beside the disassembly view:

| | off | on |
| --- | --- | --- |
| Hex | `MOV R0, #128` | `MOV R0, #&80` |
| APCS | `MOV PC, R14` | `MOV pc, lr` |
| Ranges | `{R0, R1, R2, R3, R7}` | `{R0-R3, R7}` |
| PC-rel | `LDR R11, [PC, #-120]` | `LDR R11, &00007F90` |

Hex governs the whole line, so branch targets, SWI numbers and MSR immediates
follow it. There is a lower-case option as well, which leaves SWI names and
symbols alone, because `os_writec` is not a lower-case style of `OS_WriteC`, it
is wrong. Register notation used to be a mixture - R13 and R14 printed as SP and
LR while everything else was numbered - and is now consistent whichever way the
option is set.

**Your own SWI names.** The built-in table is the OS's, so a call into your own
module read as `SWI &42C40`. Load a file of numbers and names with **SWI
names...**, or `swi load <path>` on the debug socket. `&42C40` is accepted as
written, and a file listing a chunk base matches the `X` form of the call, which
is what code being read almost always uses.

**Driving it.** The view starts ten instructions above the PC rather than at it.
The instruction about to execute has its `:` replaced by `<`, as the RISC OS
disassembler does. There is a **Step over** button, and keys, so stepping does
not mean reaching for the mouse: Return runs or pauses, Space steps, Shift+Space
steps over. Auto-step runs 1 to 200 steps a second for watching code go by.
Breakpoints, watchpoints, traps, filters, rendering options and the SWI name
file save to a session file and load back.

**Stepping without wading through the OS.** Three settings under *While
stepping, pass through*, all off unless asked for:

- **IRQ and FIQ** - a step landing in an interrupt keeps going until it is out.
- **the OS (ROM)** - the same for the ROM and the hardware vector page.
- **SWIs** - a step that executes a SWI runs it to completion and stops at the
  instruction after it, whether the handler is in the ROM or in a module in RAM.

Measured on a booted RISC OS 5.30, paused on a SWI at `&FC14C32C`: without the
SWI setting one step lands on `&00000008`, the hardware vector; with it, on
`&FC14C330`, the next instruction. **Step over** now does the same for a SWI
without any setting, which it did not before - it recognised BL and nothing
else.

A trapped SWI still stops: **Halt on SWI**, a breakpoint inside the handler, and
`SWI &FFFFFF` in your own source all outrank the filter.

**Stepping is no longer half a second per instruction.** The window read the
machine immediately after asking for a step, which reports not-stopped because
the pause has not arrived yet, and then waited for its own half-second timer to
look again. It now follows the emulator's own notification. Measured at about
6ms a step.

**A breakpoint you can put in your source.** `SWI &FFFFFF` halts the machine
wherever it executes. The emulator swallows the instruction, so RISC OS never
sees a SWI it does not know, and the halt names the SWI's own address. Code
carrying one runs unchanged on a machine that is not being debugged.

**Also:** SPSR is shown when the mode has one; a trapped exception reports the
instruction that faulted rather than the vector it stopped at; the Trace tab's
tick boxes survive closing and reopening the window; and the overlapping
`Paused: manual pause at PC 0xFNo watchpoint hit` is fixed.

Reported by **JonAbbott2**,
[#223](https://github.com/andrewtimmins/rpcemu-extended/discussions/223),
[#225](https://github.com/andrewtimmins/rpcemu-extended/discussions/225) and
[#221](https://github.com/andrewtimmins/rpcemu-extended/issues/221), while
debugging ADFFS 3.0. Several of these were fixed and then fixed again after he
measured what actually happened.

## Expansion cards: the machine editor was describing a machine that did not exist

The Podules tab said slot 0 held the USB card and slot 1 the support card. RISC
OS said slot 0 was Support, slot 1 USB and slot 2 Ethernet. The note under the
list told a third story and the documentation a fourth. None of them was what
the emulator did.

Worse, a podule configured into slot 2 was silently not fitted whenever
networking was on, because the network card had already taken that slot. The
only trace was a line in `rpclog.txt`.

The slots the machine fills itself are now decided in one place and everything
else asks. Support and USB are always fitted; the graphics card and the network
card take the next slots up when enabled, so the first slot you can assign is 2,
3 or 4 depending on the machine. Those rows are shown holding their card, named
with the same string `*Podules` prints, and they relock as you switch the
graphics card or networking. A podule that would collide is moved up, taking its
settings with it, rather than dropped - including one in a configuration written
by an earlier version.

Reported by **hubersn**,
[#254](https://github.com/andrewtimmins/rpcemu-extended/issues/254).

## A reserved CPU mode no longer ends the emulator

Writing one of the nine reserved CPSR mode values is UNPREDICTABLE on hardware,
and the emulator answered it with an error box and an exit - taking the
registers, the memory and the disassembly at exactly the moment somebody wanted
to read them. It now halts into the debugger at the instruction that did it.

Reported by **JonAbbott2**,
[#227](https://github.com/andrewtimmins/rpcemu-extended/issues/227).

## Closing a machine stops it

Close a running machine, answer the confirmation, and the machine list came back
with the machine still executing behind it - a host core at full tilt for
something you had just agreed to shut down, and a game's music still playing.
RISC OS shutting itself down now comes back to the list as well.

Reported by **JonAbbott2**,
[#222](https://github.com/andrewtimmins/rpcemu-extended/issues/222).

## Full screen

The title bar was lost after leaving full screen. `MainFrame` overrides
`IsFullScreen()` to answer with its own flag, and that flag was still set when
wxWidgets asked, so the toolkit concluded there was nothing to leave. Same
ordering mistake behind [#206](https://github.com/andrewtimmins/rpcemu-extended/issues/206)
and the 1.1.14 report that leaving full screen "appeared to do nothing at all".
This one is verified by CI on Windows rather than by hand here: there is no
Windows machine on this side.

Reported by **zurnedden**,
[#219](https://github.com/andrewtimmins/rpcemu-extended/issues/219).

## Mode changes are quicker again

A deliberate mode change no longer waits out the settling delay that exists for
the run of mode changes a boot produces. Part of
[#220](https://github.com/andrewtimmins/rpcemu-extended/issues/220), reported by
**zurnedden**, who had RISC OS 4 mode switching as instantaneous on unextended
RPCEmu and slow in 1.1.18. That issue is still open: this is the part that
measures, and the rest of it is still being looked at.

The graphics card module also keeps the colour depth across a display switch,
which is one of the reasons the Wimp could end up in a low-resolution mode after
a game - from
[#84](https://github.com/andrewtimmins/rpcemu-extended/discussions/84).

## Under the hood

- The macOS universal build no longer fails when Homebrew's two architecture
  slices are a version apart; a fat dylib is two independent binaries and each
  architecture loads its own half.
- A failed `brew update` no longer takes the whole CI matrix with it.

## Downloads

The Windows arm64 build is the interpreter. Every other download, Windows amd64
included, is the recompiler, which is several times faster.

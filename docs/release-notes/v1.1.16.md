RPCEmu Extended Edition 1.1.16. Twenty-nine commits since 1.1.15.

A maintenance release for the 1.1.x series. The second version is being built on
`main` and is not what this is; `1.x` carries fixes for the line people are
running now.

## The keyboard works again

Nothing typed reached RISC OS: no keys, no Alt+Enter to leave full screen, and no
Ctrl+Shift+F12 to shut the guest down (#162, hubersn; #157, DrDavidGee). All three
were the same fault and it arrived in 1.1.15.

The display panel creates an OpenGL canvas that covers it exactly, and forwarded
thirteen mouse events from it. Key events were not among them. That was
survivable only while the panel itself held the focus, which it never does -
asking the panel for the focus lands on the canvas, since a `wxGLCanvas` accepts
it. So the window's key handlers sat waiting for events being delivered somewhere
with nothing listening. The canvas forwards keys now, and the focus is taken back
when it is destroyed, which would have killed the keyboard a second time on any
fall back to the software display path.

**David Ramsden**, [#160](https://github.com/andrewtimmins/rpcemu-extended/pull/160).

Fixing that left three keys still missing, **on Windows only**: Return, Tab and
the arrow keys did nothing while ordinary letters were fine. Same root, one step
further along. The canvas that holds the focus did not carry the style that tells
Windows a window wants the keys used for dialog navigation, so Windows consumed
Enter, Tab and the arrows before the emulator was ever handed them - there was no
key event left to forward. The panel underneath has always carried that style,
which is why turning hardware acceleration off made those keys work. This is not
new in 1.1.16 either: the canvas has been built that way since the display moved
to the GPU in 1.1.15, and it could not be seen while no key at all was getting
through.

One caveat, and it is worth being straight about it: **#174 reports the same dead
keyboard on Windows 11 and is still open**. It came in against 1.1.15 after this
was fixed, describes the same symptom, and is expected to be the same fault - but
there is no Windows machine here, so that is an expectation rather than a
confirmation until the reporter tries this build. The same goes for the three
navigation keys above: the mechanism was read out of the wxWidgets sources and
the fix is one line, but it has been run on macOS and by CI, not by hand on
Windows.

## RISC OS 3.71, 4.39 and 6 can use the screen memory they have

More than 2MB of VRAM bought nothing on RISC OS 3.71. The desktop sat at 800x600
and refused 1152x864 even at 256 colours, which is under a megabyte. The VRAM was
never the limit; the monitor was.

RISC OS 5 is told what the display can do through a synthesised EDID block.
Earlier versions have no EDID support at all, so the mode list came from the
monitor ID pin on the VIDC connector - held here at 0, meaning a plain VGA
monitor. One bit was deciding everything.

The expansion card now carries a monitor definition and a small module that loads
it, on machines whose ROM cannot read an EDID. Nothing is written into your
`!Boot` and nothing is installed on a disc: the definition exists only while the
card does, and it is left out entirely on RISC OS 5, where the graphics card
already does the job.

Measured with 8MB of VRAM and nothing done by hand:

- **RISC OS 3.71** - 1152x864 at 256 colours now works where it was refused, and
  1280x1024, 1600x1200 and 1920x1080 all work at 16M colours. 1920x1200 is still
  refused, which is 8MB running out and nothing else.
- **RISC OS 4.39** - the same three modes at 16M colours, where before the module
  was not there at all. RISC OS 4 was discarding it unread: it used the fast
  service call table, which 3.71 accepts and 4.39 rejects with "Illegal header
  field in module", silently. It is a plain handler now.

RISC OS 6 has the same absence of EDID and should behave as these two do, but
there is no machine here running it, so that one is reasoned rather than
measured.

## The mode list is the one RISC OS will actually accept

The emulator's menus offered thirteen screen sizes where the guest's own Display
Manager offered twenty-five, for the same machine at the same moment.

The synthesised EDID declared thirteen modes, and which thirteen was fixed in the
source rather than derived from the machine. It now carries an Established
Timings III descriptor - a bitmap over forty-four VESA DMT modes, bound by no
aspect ratio - in one of the dummy descriptor slots every real monitor ROM leaves
empty, and the legacy established-timings bitmap is filled in properly as well
rather than four bits of seventeen.

Measured on RISC OS 5.30 by having the guest export its own monitor definition:
**13 modes and 12 distinct sizes before, 67 and 25 after, with nothing lost.**
1920x1200, 1920x1440, 1856x1392, 1792x1344, 1400x1050, 1360x768, 1280x768,
1152x870, 848x480, 832x624, 720x400, 640x400 and 640x350 are all new. The
emulator's own menus gained the same twelve, so the two lists agree again, and a
test now fails if a mode is added to one and not the other.

It fixes the reverse fault too, which nobody had reported: the old list was
written out whole whatever the display, so a 1080-tall monitor was offered
1600x1200 and a 1024x768 one 1280x1024 - sizes the chooser listed and RISC OS
then refused. A mode is now declared only if it fits inside the preferred one in
both directions.

1366x768 is still absent and cannot be added: DMT has 1360x768 and no 1366x768,
so there is nothing to declare it with.

## A screen size RISC OS has left can be asked for again

Change the mode from inside RISC OS - `*WimpMode`, Configure, an application -
and the size the machine was configured for could no longer be chosen from
*Settings > RISC OS Screen Size*. Picking it did nothing, and two seconds later it
was struck off the list as refused, leaving no way to ask for it at all until the
machine was restarted.

Three separate checks all compared against what had been *requested* rather than
what the desktop actually is. All three follow the desktop now, and the tick in
the menu does as well, so nothing ticked means what it says: the guest is in a
mode this list does not offer.

**David Ramsden**, [#166](https://github.com/andrewtimmins/rpcemu-extended/pull/166).

## The graphics card

- **It starts on a machine with less than 256MB** (#163, JonAbbott2). RPCEmuGfx
  and ScrollWheel both failed below 256MB, `*RMReinit` answering "Bad expansion
  card identifier" while `*Podules` listed all four cards happily. Both asked the
  Podule manager where their own card was by the address handed to them at
  initialisation, and that lookup promotes the access-speed bits before comparing
  - so it can only ever match when the recorded base already has them set, and
  the address expansion card space is mapped at moves with the amount of RAM
  fitted. Both now fall back to finding their card by asking each slot in turn,
  which is what EtherRPCEm has done since #101. Tested at 16, 32, 64, 128 and
  256MB: both load at every size, where 256MB used to be the only one that
  worked.
- **`*GfxCardOff` hands the display back without stranding the machine** (#170,
  JonAbbott2). It either refused with an error and left the card driving the
  display, or switched and took the machine down in a string of data aborts.
  Taking the display off a driver makes the kernel re-initialise the mode, and
  the mode it picks is the configured one - which, while the card is the display,
  is the card's own preferred mode. VIDC20 cannot show 2560x1440, so the change
  fails, and the machine is left describing a mode of the card's size while
  pointing at a screen area far too small to hold it. `*GfxCardOff` now drops to
  640x480 in 256 colours and reclaims the screen area before handing over, then
  asks for the mode it was in. Tested on 5.30 and 5.31, both booting onto the
  card at 2560x1440. Calling `OS_ScreenMode 11,0` directly is still not safe -
  that path is the kernel's and nothing here can reach it - and `docs/gfxcard.md`
  now says so.
- **The card answers `GraphicsV_ReadInfo`.** A driver that does not answer is
  recorded as supporting no VIDC control list items, and RISC OS then refuses any
  mode wanting ExtraBytes outright, even though this driver has always honoured
  it. Worth being honest about the size of this: ExtraBytes is only the padding
  that word-aligns a row, so it is zero for every width the emulator advertises.
  It bites on a monitor definition file you supply with an odd width at a low
  depth, which makes it a latent fault rather than one anybody is hitting, and
  that path is not exercised by any test here.
- **It is no longer offered to a ROM that cannot use it.** The card is a
  GraphicsV driver and GraphicsV is RISC OS 5's. Tick it for a 3.71, 4.39 or 6.16
  machine and nothing said so: the machine booted, the card was registered, the
  driver loaded and then declined to initialise, and what you saw was a card you
  asked for and no modes. The control is greyed out with the reason in its
  tooltip. A ROM whose version cannot be read is still offered the card, on the
  grounds that refusing a feature because the emulator does not recognise a ROM
  is the worse failure.

## The guest-side files travel with the program

The podule modules, the network and graphics card drivers, the podule ROMs and
the template CMOS are versioned with the emulator, and people were running a new
emulator against old copies of them. On Windows and Linux a release is one folder
holding both the program and your data, so anybody who kept their folder and
dropped in the new executable kept the old modules with it - and there was then
nothing on the machine to repair them from.

Those files are now embedded in the executable and extracted into the data
directory when they are not already current, which costs about 600KB. A file you
have edited is left alone until a release changes that same file; a file you have
deleted comes back, a missing module being a broken installation rather than a
preference; and a file you added is never touched. Every write goes through a
rename, so an interrupted run leaves either the old file or the new one and never
half of a module a card will then try to load. A progress window appears only
when there is something to do, which is a first run and the first run after an
upgrade.

Releases no longer ship a second copy of the payload beside the program, since
that staged copy was the one people kept across upgrades.

Two things found while doing it, both of which stopped a machine starting:

- **The Windows extraction created nothing at all**, because the code that made
  the parent directories walked an absolute path and met the drive letter first.
  The machine came up to a black screen with `!Boot` never having run, HostFS not
  being there to load. Found by CI, which is the only thing here that sees
  Windows.
- **On macOS the payload was searched for wherever your data went.** `--datadir`
  and `RPCEMU_DATADIR` were quietly deciding where the read-only files were
  looked for as well, so relocating your machines moved the search for
  `poduleroms/` with them. On top of that the code asking where the executable
  lives read `/proc/self/exe`, which does not exist on a Mac, and the empty answer
  was then tested as a relative path - so every console entry point failed with
  "could not locate RPCEmu data" precisely when run from a directory that did
  have the data. `--list-machines` and `--headless` work on macOS now; they could
  not before.

Whatever else happens, the readers fall back to the files shipped beside the
program, so the worst case is the behaviour before any of this existed rather
than a machine that will not start. `RPCEMU_RESOURCE_DIR` overrides all of it,
and wins over an extracted copy, but only when the directory it names actually
holds the files being asked for.

## Also in this release

- **The HostCmd setting is kept when the machine is running.** Ticking or
  clearing *Command socket (HostCmd)* in Machine Settings was written to the
  configuration file but not to the live configuration, and a running machine
  rewrites its whole configuration from memory when it stops - so the setting
  appeared to take and then reverted. **David Ramsden**,
  [#172](https://github.com/andrewtimmins/rpcemu-extended/pull/172).
- **The scroll wheel module was never linked.** Its build turned the object file
  straight into a binary with no link step, so relocations were never resolved.
  That had gone unnoticed because the source had no branch needing one until now,
  and the first boot after the change hung the machine on a branch to itself.
  There is a link step, and building the old source through it reproduces the
  committed binary byte for byte.
- **The loopback port used to claim a machine slot has moved out of the dynamic
  range**, which the operating system hands out to anything that asks and which
  Windows on a Hyper-V host reserves blocks of at boot. Failing to claim is not
  loud - the machine falls back to slot 0 and runs - so the symptom was two
  machines given the same guest addresses.
- **`RPCEMU_RESOURCE_DIR` works alongside `--datadir` and `RPCEMU_DATADIR`**,
  which is the combination you need when your machines and the shipped files live
  in different places. It was documented as working and did not.
- **`1.x` builds and tests on every push.** The workflow named `main` alone, so
  after the branch rename this release would have been published without a single
  job having run.

RPCEmu Spork Edition 1.1.12. Seventy-one commits since 1.1.11.

## USB: real devices from the host, in RISC OS

The machine now has a USB controller, and host devices plugged into your computer
appear to RISC OS as if they were plugged into it.

- **An emulated OHCI controller** on its own expansion card, carrying RISC OS
  Open's own USB stack in its ROM.
- **Mass storage**, read and written. A USB stick's contents appear under SCSIFS.
  FAT volumes need Fat32FS, which is not bundled.
- **Streaming devices**, so a real webcam enumerates and delivers video to the
  guest, at around 90 KB/s in testing.
- **DMA memory** for the stack on a machine with no PCI, via our own support
  module.

**Verified on Linux only.** Windows and macOS releases now ship libusb, which
earlier ones did not, so USB should work there and has not been tested. Reports
welcome. See `docs/usb.md` for per-platform setup, and the licence record for the
ROOL modules we carry.

## 26-bit guests work under the recompiler

RISC OS 3.71 and other 26-bit ROMs died during startup with a data abort and
"branch through zero" unless you used the interpreter.

In 26-bit mode a compare with the S bit and RD = 15 is not a compare: TSTP, TEQP,
CMPP and CMNP write the PSR, and so can change processor mode, which RISC OS 3
does constantly. The recompiler compiled them as ordinary flag-setting compares
and discarded the mode change. The interpreter and the old 32-bit x86 backend both
handled it correctly; the amd64 backend had lost the check, and the arm64 backend
inherited that.

Reported on an Intel Mac and long assumed to be macOS-specific. It was not: it
reproduced on Linux with any 26-bit ROM.

## Memory protection: the ADFFS defect

A cached MMU translation was reused without rechecking access permissions, so an
illegal access following a legal one to the same page was allowed. ADFFS has
advised against RPCEmu because of this since 2013. Permissions are now checked on
every access, cached or not, with a regression test covering the ARM DDI 0100B
rules. An unmapped PC is also reported to the guest rather than killing the
emulator.

## Faster, and more responsive

- **Input latency**: under "Reduce CPU usage" the host input queue was being
  drained once or twice a second, so the pointer and keyboard lagged by up to a
  full second. Fixed (issue #36).
- **Around 8% more guest throughput**: the recompiler now handles logical
  instructions whose immediate has a rotate, instead of calling the interpreter
  for each one. Measured on an otherwise idle core, best of five.
- **The graphics card's framestore** is reached through the memory fast map for
  both reads and writes, and the fast map is large enough to behave as a cache.
- A sampling profiler for the emulator thread, for development builds.

## Elsewhere

- **Package manager**: the repository list is yours to edit, JASPP is included,
  and it warns that ADFFS needs the graphics card turned off, since the two cannot
  be used together.
- **Display**: a downloaded machine comes up at the host display's size, and the
  mode table no longer imposes a ceiling of its own.
- **Discs**: each sector write is flushed, so killing the emulator can no longer
  leave a corrupt ADFS filesystem.
- **Kinetic**: how the card works is now documented, including why its VRAM is
  fixed at 2MB.
- **Builds** on distributions whose wxWidgets lacks wxWebRequest, which includes
  Debian bookworm and so Raspberry Pi OS. The package manager and Get RISC OS are
  absent in that case; everything else works.

## Known limitations

- **arm64 builds ship the interpreter.** A native AArch64 recompiler exists in the
  source and passes its differential tests, but does not yet boot a machine, so it
  is not enabled. Issue #30 tracks it, and this release adds the tools that
  reproduce it without arm64 hardware: `RPCEMU_JIT_DENY` and a headless boot
  harness. The macOS arm64 slice is likewise the interpreter.
- **USB is tested on Linux only**, as above.
- **The binaries are unsigned.** Windows Defender's machine-learning heuristic
  sometimes reports a recompiler build as Trojan:Win32/Wacatac.C!ml. It is a false
  positive: a JIT writes machine code into memory and then executes it, which is
  what the model is looking for. Check the file against the hashes on this page if
  you want to be sure.

RPCEmu Extended Edition 1.1.18. Five commits since 1.1.17.

A maintenance release for the 1.1.x series, made up entirely of things people
reported. The largest is that RISC OS 4 and 3.7 could not reach the big screen
modes any more, and the reason turned out to be something this emulator was
telling RISC OS rather than anything RISC OS was doing.

## The large screen modes are back on RISC OS 4 and 3.7

RISC OS 4.02 with 16MB of VRAM would no longer take `WimpMode X3840 Y2160 C256`,
a mode that worked in 1.1.13. The graphics card option being greyed out on 4.02
looked like the cause and was not; it is unrelated, and it is telling the truth,
because the card needs an interface that only RISC OS 5 has.

Two separate things were in the way, and both are fixed.

**A monitor definition that stopped at 2048 pixels.** The versions of RISC OS
with no EDID support are given a monitor definition by the emulator, because
without one they fall back to a single bit on the video connector and conclude
you have a plain VGA monitor. That definition is generated from the emulator's
own list of modes, and it was dropping everything wider than 2048 - so the widest
mode RISC OS 4 was ever told about was 1920x1440. The emulator was not refusing
the mode. RISC OS was, because nothing had told it the mode existed. That
definition arrived in 1.1.16, which is why 1.1.13 could do it and nothing since
could.

**A colour depth nobody asked for.** Separately, the screen size list reserved
room for 32 bits per pixel whatever depth you actually wanted. At that depth
3840x2160 needs 33MB, which no machine here can be configured to have, so the
mode was filtered out on every machine and every version of RISC OS. In 256
colours the same mode needs 8MB and fits 16MB of VRAM comfortably. A size you
name yourself is now budgeted at the shallowest depth, and only a size the
emulator picks for you still assumes the deepest.

Measured on both, each booted to its desktop and the resulting mode read back off
the screen rather than assumed:

| | | |
| --- | --- | --- |
| RISC OS 4.39 | 16MB VRAM | 3840x2160 at 256 colours |
| RISC OS 3.71 | 8MB VRAM | 3840x2160, 3440x1440 and 2560x1440 |

What still limits a mode is the screen memory fitted and the colour depth, which
RISC OS checks for itself. The deepest colours are not available at the largest
sizes - 3840x2160 is 8MB in 256 colours and 33MB in 16 million - and the note
under the setting now says so rather than leaving you to find out.

Reported by **zurnedden**,
[#207](https://github.com/andrewtimmins/rpcemu-extended/issues/207), who pinned
it to the exact version that still worked, which is what made it findable, and
whose question about monitor definition files is what turned the fix around after
the first attempt addressed only the second of the two causes.

## The menu bar came back after full screen

On Windows, leaving full screen left the window with no menu bar - no File, no
Disc - while the tool bar returned normally. That asymmetry was the whole clue.

Going full screen hid the menu bar and the tool bar by hand and then asked
wxWidgets to go full screen with the flags that tell it to hide them too. One
piece of state with two owners, and on Windows the second owner does not repeat
what the first did, it changes it: wxWidgets deliberately declines to restore a
bar that was already hidden when it started. Both bars are now left entirely to
wxWidgets, going in and coming out.

The emulator also now records the state of the menu bar, tool bar and status bar
either side of a full screen change, and on Windows asks the operating system
directly whether the menu is still attached. If this ever misbehaves again, the
log says so in one line.

Reported by **zurnedden**,
[#206](https://github.com/andrewtimmins/rpcemu-extended/issues/206).

## Pointing a new machine at an existing HostFS folder

Creating a machine and giving it a HostFS folder elsewhere on the disc froze the
window for a minute or two and then offered to move files from a folder that had
never held any.

A new machine's HostFS was never empty. It carried one inherited file,
`Network/ReadMe,fff`, which described a networking setup removed years ago and
linked a manual belonging to another project. Because something was in there, the
emulator correctly reported that there was something to move. That file is gone,
so a new machine now gets a genuinely empty HostFS, and the check itself now asks
whether anything has been *put on* the disc rather than whether the folder is
empty - which covers machines created with earlier builds too.

The freeze was separate. Both folders were being walked and measured twice over
for one answer, which on a full HardDisc4 is tens of thousands of files, with
nothing on screen to say the emulator was still alive. It is measured once now,
and says what it is doing while it does it.

**You may notice** that a machine created with this build has nothing in its
HostFS folder at all. That is the fix, not a fault.

Reported by **riscos-richard**,
[#204](https://github.com/andrewtimmins/rpcemu-extended/issues/204), who worked
out the cause himself from what was left in the folder.

## Access sharing chose a VPN over the network

With a VPN connected, the Access broadcast relay bound itself to the VPN's
adapter, so broadcasts went somewhere no Acorn could hear them and disconnecting
the VPN was the only way to get the real adapter back.

The relay took the first interface that was not loopback, which is wrong on any
machine with a VPN client, a hypervisor or a container runtime on it. Candidates
are now scored: a real wired or wireless adapter counts for a great deal, a
tunnel counts heavily against, and on Windows the adapter type does most of the
work. Every candidate and the decision are written to the log, so it is possible
to see what was chosen and why.

Where the scoring is wrong, `relay_interface` in the application settings names
an adapter outright. Part of the name is enough - `Realtek` will match a long
description - and it is matched against the interface name on Linux and macOS and
against both the name and the description on Windows. A name that matches nothing
says so and falls back rather than quietly pretending it was obeyed.

This only ever affected Windows. On Linux and macOS a VPN tunnel is not a
broadcast interface and was never a candidate.

Reported by **riscos-richard**,
[#205](https://github.com/andrewtimmins/rpcemu-extended/issues/205), who read the
code and correctly identified that there was no way to override the choice.

## Upgrading

Nothing to do. Machines, discs and settings carry over untouched, and the new
`relay_interface` setting is optional and empty by default.

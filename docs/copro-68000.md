# 68000 co-processor

The Motorola 68000, as a processor for the OPEN Bus co-processor card. Fit it with
`--openbus-card=68000`, or from the machine editor's **Co-Processor Card** tab. It
reaches the Macintosh Plus and SE, the Atari ST, the Amiga and the Mega Drive.

**Not finished.** The design below is settled and the code is being written
against it.

The card itself, its register map, the `RPCEmuCoPro` module and the SWIs are in
[openbus.md](openbus.md). Source is `src/copro/cpu_68000*.c`, tested by
`tests/test_cpu_68000.c` and `tests/test_68000_vectors.c`.

**A 68000 reaches System 7.5.5**, and Mac OS 8.1 needs an '040. Mac OS 9 is
PowerPC-only, so nothing here will run it.

## What is implemented

The documented instruction set, all twelve addressing modes, both privilege levels
and the exception model in full: the vector table at address 0, the three
exception groups with their stack frames, seven prioritised interrupt levels, and
both autovectored and vectored interrupts.

That last part is not optional for this processor the way it would be for an
8-bit. An Atari ST or Mac Plus ROM installs a vector table and runs its operating
system in supervisor mode within a few instructions of reset, so a core without
privilege levels could not begin to run one.

## What is not

Undocumented behaviour, the 68010 and 68020, the FPU and any MMU. The 68008's
narrower bus changes its timing and nothing else a program can see, so it is not
offered separately.

The `RESET` instruction asserts a line no card here has, so it is a no-op that
costs its documented cycles.

## The state

D0-D7, A0-A7 with A7 aliasing the user or supervisor stack pointer by mode, PC,
and a full status register: the supervisor bit, the trace bit, the three-bit
interrupt mask, and the condition codes in the low byte.

Big-endian, as the 6809 and the 6800 are.

## Privilege and exceptions

The vector table is 256 vectors at address 0, and exceptions divide into the three
groups the datasheet divides them into: bus error and address error with the long
frame; trace, interrupt, illegal instruction and privilege violation; and the
sixteen TRAPs with TRAPV, CHK and divide-by-zero. The privilege switch happens on
exception entry and on `RTE`.

**A word or long access to an odd address takes an address error**, as the part
does, with the long stack frame. Code written for a 68020, which removed the
restriction, is exactly the code that appears to work and does not on the part
being emulated.

### An uninstalled vector faults rather than jumping

Real hardware reads the vector and goes there, so a vector that has never been
written sends the processor to address 0 to die somewhere unrelated. The card
reports a fault with a named cause instead: "took a privilege violation with no
handler installed" is more use than a jump into nothing.

This is the only deliberate divergence in the exception model. A guest that wants
the hardware behaviour installs a vector pointing at its own code, which is what a
real machine's ROM does anyway.

## How a program stops

`STOP` loads the status register and stops the processor, and that one behaviour
covers both cases without a special case. If nothing interrupts the core it is
finished: the card reports it halted and D0 is the exit code, as A is on the
Motorola 8-bits. If the guest offers an interrupt, the core resumes, which is what
the instruction means.

`SYNC` and `CWAI` fault on the 6809, and `WAI` on the 6800 and the 65C02, because
those cards have no interrupt model to wait on. This one does, which is why `STOP`
does not need to fault.

## Reset

Reset takes its program counter from the card's `ENTRY` register, as every other
core does, rather than fetching the reset vector from addresses 0 and 4. The status
register comes up supervisor with the interrupt mask at 7, which is the real reset
state.

**This is the one place the core is deliberately less authentic.** A guest booting
a real ROM reads the reset vector itself and sets `ENTRY` and the supervisor stack
pointer through `CoPro_Registers`, which are calls it is already making, and the
core keeps a contract identical to the other six.

## Interrupts

Seven prioritised levels, autovectored or vectored, and they map onto `IRQCTRL`
with nothing invented: the three-bit level field is exactly seven levels, and the
vector-byte field that exists for a Z80 in mode 2 is what a vectored interrupt
needs.

Level 7 is effectively non-maskable, being edge-triggered and taken whatever the
mask says, so `IRQCTRL`'s `IRQ_NMI` bit maps onto it.

## Card RAM

| | |
| --- | --- |
| Default | 1MB |
| Maximum | 16MB |
| Flat limit | 16MB |

The 68000 has 24 address lines, so unlike RV32IM's 64MB the ceiling is not a
judgement about how much is enough - it is the whole of what the part can name,
and addresses wrap at 24 bits as the hardware does. 16MB is this part's flat
limit, where for the 8-bit cores the same figure is a paged ceiling reached by
banking.

## Decoding

A 65,536-entry dispatch table, built at initialisation from the encoding rules.

The 6809's opcode map is a grid, so that core takes an opcode apart
arithmetically. This one is not: group `4xxx` alone holds NEG, CLR, MOVEM, LEA,
JMP, JSR, EXT, SWAP, TAS, ILLEGAL, TRAP, LINK, UNLK, RESET, NOP, STOP, RTE, RTS,
RTR and the moves to and from SR, CCR and USP, and a hierarchical switch over that
is four levels deep and illegible.

★ **The table is generated, never typed.** Building it means looping over all
65,536 words once, in one place, and asking what each is - and the cycle costs are
built in the same pass from the same rules, so a valid encoding cannot end up with
no cost or with one that disagrees about its operand size. It also makes "does
this encoding exist?" a single lookup, which is how the 6809 and the 6800 refuse
an illegal opcode.

## Cycles

Not one number per opcode. An instruction costs a base for its operation and size,
plus the cost of calculating its effective address, which depends on the mode and
the size again. Both tables are built in the pass that builds the decode.

The 6809's timings were derived from group rules and cross-checked against 83
datasheet values read separately, and the 6800's against 65 - which is the same
person reading the same document twice. The vector suite below carries per-cycle
bus transactions, so this core's timing is checked against a different
implementation entirely.

Memory contention is not modelled, as it is not for any core here.

## The stall protocol

Every core here answers a stalling access by abandoning the whole instruction and
retrying it, which assumes the stalling access is the first thing in the
instruction to have an effect outside the registers. See the note in `cpu_mem.h`.

★ **`MOVEM`, `MOVEP` and the exception frames carry a transfer counter**, so a
retry continues from it rather than starting again. `MOVEM` writes up to sixteen
registers to memory in sixteen accesses, so whole-instruction retry would write
the first eight twice if the ninth stalled, with nothing reporting it. Every other
instruction keeps whole-instruction retry unchanged.

`TAS` needs nothing: it is read-modify-write, so a stall lands on its read, which
`cpu_mem.h` already covers.

Saving the registers before each instruction is about 72 bytes on this part,
against 11 on the 6809 and 6 on the 6502. It is gated on the hook's `can_stall`
flag, so a card with no stalling region pays nothing.

## Registers through `REGSEL`

0 to 7 are D0-D7, 8 to 15 are A0-A7, then 16 is the program counter, 17 the status
register, 18 the user stack pointer and 19 the supervisor stack pointer.

## Files

Four sources behind one header, so the card, the core-ops table and the tests see
one core as they do for the others.

| File | What is in it |
| --- | --- |
| `cpu_68000.h` | The whole public interface |
| `cpu_68000.c` | The dispatch table's construction, decode, `step` and `run` |
| `cpu_68000_ea.c` | The twelve addressing modes and their cycle costs |
| `cpu_68000_exc.c` | Privilege, the vector table, the three exception groups |
| `cpu_68000_ops.c` | The instruction implementations |

Every other core is a single file. This one is not because the practical limit is
what can be held in view at once and edited reliably: the Z80 at 2116 lines is
already the awkward one, and this part is nearer four thousand.

## Testing

`tests/test_cpu_68000.c` is hand-written, in the manner of the other cores, and
covers what vectors structurally cannot see: the card integration, the aperture,
the stall-and-retry path including a resumed `MOVEM`, a supervisor-to-user
transition across an exception, and an uninstalled vector faulting.

`tests/test_68000_vectors.c` drives
[SingleStepTests/m68000](https://github.com/SingleStepTests/m68000), which is
MIT-licensed test **data**: per-instruction initial and final state of every
register, the status register and the RAM touched, plus the bus transactions. The
runner is ours, so nothing is derived from anybody's code.

This is the argument that recommended RV32I for having a compliance suite, applied
here: the 68000's encoding space is thousands of instructions, and a few hundred
hand-written checks would cover what was thought of and say nothing about the rest.

Two things to be honest about. The vectors are generated from MAME's microcoded
68000, so they encode that implementation's reading of the part rather than
silicon; where the core and the vectors disagree the datasheet decides, and the
answer is worth recording where it happens. And the checkout is 110MB, so it is
gitignored and fetched by a script, as the Arculator reference is - the test skips
cleanly when it is absent, so a fresh clone and CI stay green without it.
